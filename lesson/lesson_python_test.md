# 经验教训总结

## 问题描述 1：先写报告后测试

在生成测试用例时，**先编写了测试报告，后运行测试验证**。测试报告中的结果并非来自程序，导致与实际代码行为不符。

### 具体错误

1. **TC-E-006 测试用例**: 报告中预期 "无效的 data_key 应该返回空结果"
   - 实际代码行为: data_key 不存在时，代码继续处理整个 json_data
   - 修正后: `assert result["frame_count"] == 1`

2. **其他用例风险**: 虽然大部分测试通过了，但这是运气，而非基于实际验证

## 问题描述 2：基于真实数据结构"造"数据，而非直接使用真实数据

在生成的测试用例时，虽然用户明确要求使用的真实数据，但我错误地选择了**手动构造**类似真实数据结构的数据，而非直接加载真实文件。

### 具体错误

**我的错误做法**:
```python
# 错误：手动构造数据
@pytest.fixture
def sample_dyn_data(self):
    return {
        "1772765613.9666445": {  # 手动编造的时间戳
            "header": {"time_stamp": 1772765567.6060176, "seq": 0},
            "dyn_sts_feedback": 2,
        },
        ...
    }
```

**正确做法**:
```python
# 正确：直接加载真实文件
REAL_DYN_FILE = LOADING_DIR / "<real_file_path>"

@pytest.fixture
def real_dyn_data(self):
    with open(REAL_DYN_FILE, 'r') as f:
        data = json.load(f)
        return data
```

### 使用真实数据的好处

| 维度 | 构造数据 | 真实数据 |
|------|----------|----------|
| **数据完整性** | 容易遗漏字段 | 包含所有真实字段 |
| **边界值** | 基于假设 | 反映真实边界 |
| **测试可信度** | 低（可能不符合实际） | 高（来自真实场景） |
| **发现问题能力** | 弱 | 强（可能暴露未预期的问题） |
| **维护成本** | 高（需同步更新） | 低（直接使用文件） |

## 关键教训

> **永远不要在没有运行测试的情况下，编写测试报告的预期结果。**

测试报告应该是测试运行的总结，而非测试前的猜测。

---

> **当用户指定了数据来源时，必须直接使用指定的数据，不要自行构造。**

构造数据可能遗漏真实数据的边界特征，降低测试的有效性。

---

> **真实数据 >> 构造的数据**

直接使用真实文件，既节省工作量，又提高测试可信度。
